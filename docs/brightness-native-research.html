外接屏亮度控制原生化方案调研

目标：去除低亮度模式对 BetterDisplay 的第三方依赖，在应用内原生控制所有显示器的亮度。调研覆盖 6 个方向 + 2 个补充专题，关键 API 均在本机（M4 Pro，macOS 26.6）实测验证。

结论

可以完全去除 BetterDisplay 依赖。BetterDisplay 在底层使用的 IOAVService 私有接口由 macOS 公共 IOKit 框架导出，本机实测全部符号与 IORegistry 节点在 macOS 26 上存在且结构未变，MonitorControl（MIT 许可）提供了经过大量用户验证的同路线开源实现，核心代码 275 行、无外部依赖，可直接移植。

推荐方案为三层结构：DisplayServices（系统原生亮度）→ DDC/CI（硬件背光）→ 遮罩窗口（软件调暗兜底），按显示器逐台检测路由。预计总工作量 3–4 个工作日。

另有一项前置事项：现有内建屏亮度功能在应用内失效，但 DisplayServices API 本身经实测正常，失效原因在应用侧，原因未查明，重建前需先定位（见第 9 节）。

1现状与依赖点

低亮度模式的功能是：鼠标抖动运行期间把所有显示器亮度降到最低，停止后恢复原值。当前实现分两条路径：

  • 内建显示器：dlopen 加载私有框架 DisplayServices，调用 DisplayServicesGetBrightness / SetBrightness（BrightnessControl.swift）。该路径无第三方依赖，但当前在应用内失效（原因未查明，API 层已排除，见第 9 节）。
  • 外接显示器：通过 DistributedNotificationCenter 调用 BetterDisplay 的 Integration API（BetterDisplayManager.swift），要求用户安装并运行 BetterDisplay 且开启其集成功能。这是唯一的第三方依赖，也是本次调研要替换的部分。

对方案选择有利的工程条件：应用不走 Mac App Store、未启用 App Sandbox（entitlements 中显式关闭）、已开启 Hardened Runtime 且验证过加载私有框架可行、最低部署版本 macOS 26.0、Xcode 工程使用文件夹同步组（新增源文件不需要改 pbxproj）、无任何 SPM 依赖。

2本机实测结论

以下事实在本机（M4 Pro，macOS 26.6 / Darwin 25.6，接有一台 Dell U2720Q 外接屏）直接验证，置信度为最高级：

验证项结果
IOAVServiceCreateWithService / ReadI2C / WriteI2C 符号存在，由公共框架 IOKit.framework 导出（dyld_info -exports 确认），链接后 extern 声明即可调用，不需要 dlopen
IORegistry 中 DCPAVServiceProxy 节点存在 14 个，带 Location = "Embedded" / "External" 属性，与 MonitorControl / m1ddc 源码的假设一致
DisplayServicesGet/SetBrightness 对内建屏读取、写入、恢复全部成功（写入测试实际改变了亮度并恢复）
DisplayServicesCanChangeBrightness存在；内建屏返回 true，Dell 外接屏返回 false
DisplayServicesGetBrightness 对普通外接屏返回错误码 1000，确认普通第三方外接屏必须走 DDC/CI
DisplayServicesSetBrightness 对普通外接屏返回 0 但无实际效果（假成功），检测支持性不能依据 Set 的返回值
CGSetDisplayTransferByTable（gamma 表）API 调用成功、读回一致；视觉生效无法程序化验证
已移除的符号DisplayServicesBrightnessChanged、CoreDisplay_Display_SupportsUserBrightness 在 macOS 26 上不存在——私有符号必须全部判空处理

3推荐方案：三层路由

对每台在线显示器（CGGetOnlineDisplayList 枚举）按以下顺序检测并路由，检测结果在显示器配置变化（CGDisplayRegisterReconfigurationCallback）时重建：

L0 前置排除：虚拟显示器 AirPlay、Sidecar、DisplayLink 坞输出的虚拟屏（kCGDisplayIsVirtualDevice）没有可用的硬件亮度通道，直接进入第 3 层。镜像模式先经 CGDisplayMirrorsDisplay 解析到真实显示器。
↓ 物理显示器
L1 DisplayServices —— 系统原生亮度 覆盖内建屏和 Apple 生态外接屏（Studio Display、Pro Display XDR、LG UltraFine）。试读检测：Get 返回 0 且值 ≥ 0 即支持。复用现有 DisplayServicesBackend，新增约 30 行。
↓ Get 试读失败（返回 1000）
L2 DDC/CI —— 硬件背光控制 覆盖绝大多数第三方外接屏。Apple Silicon 走 IOAVService + DCPAVServiceProxy，移植 MonitorControl 的 Arm64DDC.swift（MIT，275 行）。真正降低背光、降低功耗，与 BetterDisplay 的底层机制相同。
↓ DDC 读取失败（重试后）/ 显示器不支持 / Intel 机型
L3 遮罩窗口 —— 软件调暗兜底 每屏覆盖一个黑色高层级 NSWindow（照 MonitorControl 的 shade 实现）。公开 AppKit API，对任何显示器一律有效，进程退出后窗口必然消失，恢复可靠性最高。不降低背光功耗。

这个结构与 MonitorControl 的生产方案一致（Apple 屏走 DisplayServices、普通屏走 DDC、虚拟屏走遮罩），每一层都有开源先例可对照。三层各自独立，可以分阶段落地：先做 L1 + L3 就能覆盖全部显示器（L3 保证功能下限），L2 提供真实背光控制作为第二阶段。

4第 1 层 · DisplayServices

系统设置里能直接调亮度的显示器（内建屏、Apple Studio Display、Pro Display XDR、LG UltraFine 系列），第三方非沙盒应用都可以用同一组 DisplayServices 函数控制，不需要任何 entitlement。MonitorControl 对这类屏只用 DisplayServicesGetBrightness / SetBrightness 两个函数（源码级确认，AppleDisplay.swift）。

检测方法（照 MonitorControl 的 isAppleDisplay）

func supportsNativeBrightness(_ id: CGDirectDisplayID) -> Bool {
    // 1. 防第三方 HDR 屏误报（macOS 15+ 例外分支；0x610 = Apple vendor）
    if CGDisplayVendorNumber(id) != 0x610,
       cgsIsHDRSupported?(id) == true, cgsIsHDREnabled?(id) == true {
        return CGDisplayIsBuiltin(id) != 0
    }
    // 2. 试读检测（核心）：Get 成功且值非负 => 支持原生控制
    var b: Float = -1
    if dsGetBrightness(id, &b) == 0, b >= 0 { return true }
    return CGDisplayIsBuiltin(id) != 0
}

要点：

  • 检测依据只能是 Get 试读或 CanChangeBrightness。Set 对不支持的屏返回 0 且无效果（本机实测确认），返回值没有判定价值。
  • 白名单方式不可行：LG UltraFine 的 vendor 为 LG，按 Apple vendor 过滤会漏判。
  • CGSIsHDRSupported / CGSIsHDREnabled 来自 SkyLight 框架，本机实测可用；这两个符号与所有私有符号一样必须判空。
  • 不引入 CoreDisplay 的亮度函数：CoreDisplay_Display_GetUserBrightness 在 Apple Silicon 上对任何屏都返回 1.0，无法区分状态（本机实测 + nriley/brightness 源码注释相互印证）。

Apple 生态外接屏没有实机验证，结论来自 MonitorControl / Brightness-Sync 源码与多个独立来源交叉印证 MEDIUM，建议发布前找有 Studio Display 的用户实测。

5第 2 层 · DDC/CI

DDC/CI 是显示器行业标准协议，通过视频线内的 I2C 通道读写显示器设置，亮度对应 VCP 代码 0x10。BetterDisplay、MonitorControl、Lunar、m1ddc 控制外接屏背光走的都是这条协议。

5.1 Apple Silicon 实现路线

调用序列（MonitorControl Arm64DDC.swift 与 m1ddc 源码逐行核读，两者交叉一致 HIGH）：

  1. 声明符号：IOAVService 四个函数由公共 IOKit 导出，bridging header 里 extern 声明约 6 行，加 CoreDisplay_DisplayCreateInfoDictionary（CoreDisplay 导出）。
  2. 枚举与匹配：递归遍历 IORegistry 的 IOService plane，找 framebuffer 节点（IOObjectConformsTo(service, "IOMobileFramebuffer")，一次覆盖 M1 的 AppleCLCD2 与 M2 Pro 之后的 IOMobileFramebufferShim），迭代序列中紧随其后的 DCPAVServiceProxy 节点且 Location == "External" 时调 IOAVServiceCreateWithService 创建服务。多显示器必须逐个创建，无参的 IOAVServiceCreate 只返回默认的一个。
  3. 与 CGDirectDisplayID 对应：简单做法（m1ddc）用 CoreDisplay_DisplayCreateInfoDictionary 的 IODisplayLocation 路径直接定位 registry 节点；完备做法（MonitorControl）用 EDID UUID 分段 + 位置路径 + 序列号打分后贪心分配，可区分多台同型号显示器。建议采用打分法。
  4. 读写 DDC 包：I2C 地址 0x37、子地址 0x51。写亮度 6 字节包 [0x84, 0x03, 0x10, hi, lo, chk]；读亮度先写请求 [0x82, 0x01, 0x10, chk]，等待 50ms 后读回 11 字节，其中第 7–8 字节为 max、第 9–10 字节为当前值（大端）。校验和为逐字节 XOR。

5.2 时序参数（MonitorControl 默认值，源码确认）

参数取值说明
写前延迟10 ms每次 I2C 写之前
写重复次数2 次同一包连写两遍，防止部分显示器丢包（写操作幂等）

5.3 MacAfk 的调用流程

  1. 抖动开始：逐屏串行读 VCP 0x10 得到 (current, max)，两个 raw 值持久化到磁盘；读失败（重试用尽）的屏降级到第 3 层，不盲写。
  2. 写入最低值：写 0（clamp 到 [0, max]）；可选 50ms 后读回验证（HDR 模式的屏可能忽略写入且无错误返回）。
  3. 抖动停止：写回持久化的 raw current 值。恢复前先读回当前值：与自己写入的低值不一致时说明期间被用户或其他工具改过，跳过恢复。验证时容忍 ±1（显示器内部换算误差）。
  4. 启动时检查磁盘上是否有未恢复的残留值（进程曾异常退出），有则补恢复——DDC 写入的是显示器自身的持久设置，进程退出不会自动回滚，这是把原值持久化的主要理由。
  5. 睡眠 / 唤醒 / 显示器配置变化期间挂起 DDC 操作，唤醒后延迟再恢复；服务映射在配置回调里重建。

5.4 已知硬件例外

硬件情形现象处理
M1 全系（及部分入门款 M2）内建 HDMI 口该口经 MCDP29xx 转换芯片，标准 0x37 地址不通检测 DCPAVServiceProxy 父节点 EPICProviderClass == "AppleDCPMCDP29XX"，改用地址 0xB7（m1ddc PR #60，2026-08 合入）。按属性检测而非按芯片代数硬编码，两种口径的资料差异不影响实现
M2 Pro/Max 及之后的 HDMI 2.1 口不经转换芯片0x37 直接可用（用户实测报告）
HDR 模式开启的显示器可能锁定或忽略 DDC 亮度命令，无错误返回写后读回验证作为生效判据，无效则降级第 3 层
三星 Smart Monitor / 电视类产品不支持 DDC/CI；部分品牌出厂默认关闭 DDC/CI读不到 VCP 0x10 按正常路径处理（降级），不作为错误
个别显示器DDC 通道在特定电源状态下停止响应（断电数秒或打开 OSD 菜单可恢复）重试用尽后放弃本次操作

实现要点（照 MonitorControl 的 shade 生产实现）：

let shade = NSWindow(contentRect: .zero, styleMask: [], backing: .buffered, defer: false)
shade.backgroundColor = .clear
shade.ignoresMouseEvents = true              // 不拦截鼠标抖动
shade.level = NSWindow.Level(rawValue: Int(CGShieldingWindowLevel()))
shade.collectionBehavior = [.stationary, .canJoinAllSpaces, .ignoresCycle, .fullScreenAuxiliary]
shade.contentView?.wantsLayer = true
shade.contentView?.layer?.backgroundColor = CGColor.black
shade.contentView?.alphaValue = 0.97         // 压暗程度；1.0 全黑（OLED 像素熄灭）
shade.setFrame(screen.frame, display: true)
shade.orderFrontRegardless()
// 恢复：close()；屏幕配置变化时销毁全部遮罩并延迟约 1s 重建

说明：软件调暗只改变显示内容，外接 LCD 的背光功耗不变（OLED / miniLED 屏在全黑内容下实际降低功耗）；遮罩层级低于锁屏界面，与防锁屏主功能无冲突。界面文案上应注明该屏走的是软件调暗。

7Intel 机型的处理

macOS 26 支持的 Intel 机型仅 4 款（Mac Pro 2019、MacBook Pro 16" 2019、MacBook Pro 13" 2020 四雷电口、iMac 27" 2020），且 Tahoe 为最后一个支持 Intel 的大版本。Intel 上 IOAVService 路线完全不存在，DDC 需另走 IOFramebuffer + IOI2CSendRequest（IOKit 公开头文件 IOKit/i2c/IOI2CInterface.h，macOS 26 SDK 中完整保留）。

建议：第一阶段 Intel 机型不做 DDC，外接屏统一走第 3 层遮罩兜底。依据：受众极小且只减不增；团队无 Intel 测试机时，读回复延迟等参数（Intel 核显与 AMD 独显差异大，minReplyDelay 取值不当有内核崩溃风险，ddcctl 源码注释引用 Apple 文档警告）无法实测调优；MonitorControl 的 IntelDDC.swift 虽标注 MIT，但其代码来源链上游包含 GPLv3 项目和一个无许可证仓库，直接复制存在许可证争议（见第 10 节）。如后续确有 Intel 用户需求，按公开 API + VESA 规范自行重写约 200–260 行即可，无私有符号障碍。

8与其他亮度工具的共存

macOS 在 IOAVService / IOI2CInterface 层没有跨进程的 DDC 请求串行化（各开源实现源码确认只有进程内队列），两个进程并发读写同一显示器会互相破坏 DDC 事务。BetterDisplay、Lunar、MonitorControl 的亮度同步 / 自动亮度 / 唤醒恢复功能都会用各自内部记录的值覆写外部写入。因此：

  • 检测到 BetterDisplay 在运行时避让：继续通过现有 Integration API 通道读写（保留 BetterDisplayManager 作为可选通道），不直写 DDC。注意现有代码里的 bundle id me.waydabber.BetterDisplay 为旧版本标识，现行版本为 pro.betterdisplay.BetterDisplay，两个都要精确匹配。这样对存量 BetterDisplay 用户的行为不变，新用户则不再需要安装它。
  • 检测到 Lunar（fyi.lunar.Lunar）或 MonitorControl（me.guillaumeb.MonitorControl）运行时：首次提示两者的自动化功能可能与低亮度模式互相覆盖，附「不再提示」选项，不阻止功能运行。Lunar 与 MonitorControl 自身都有同类冲突检测与提示的先例。
  • 恢复前读回校验（第 5.3 节第 3 条）是与所有自动化工具共存的关键防线，成本低且不依赖检测覆盖完整。
  • 读回复时校验 VCP 代码：MonitorControl 的读实现只校验 checksum，跨进程交错时可能把其他进程请求的回复当作自己的数据；移植时补一行 reply[4] == 0x10 检查。

9风险与未决问题

事项说明应对
应用内 DisplayServices 失效内建屏亮度控制在应用内不工作，而同一 API 在本机独立进程实测正常。原因未查明重建前先在应用进程内复现定位（打包环境、调用时机、日志），确认后再决定 L1 层直接复用还是修正
私有 API 无兼容承诺DisplayServicesBrightnessChanged 在 macOS 26 被移除即为实例。IOAVService 系列虽由公共框架导出但无文档所有私有符号 dlsym / 弱链接判空，缺失时逐层降级（最终落到第 3 层公开 API）；BetterDisplay / MonitorControl / Lunar 同依赖这些接口，系统变更时社区会快速适配
DDC 兼容性长尾不同显示器 / 线材 / 坞的 DDC 行为差异大，读失败率高重试 + 读失败降级第 3 层保证功能下限；发布后按用户反馈补充例外清单
Apple 生态外接屏无实机验证Studio Display / UltraFine 的 L1 结论来自源码与多来源交叉印证发布前邀请用户实测，或首个版本对这类屏同时保留 L2 探测
时序参数的来源差异调研中的两处数值口径差异（标准读延迟与 MCDP29xx 读延迟均为 50ms；Intel 读校验和的初值写法两家不同）实现时以 MonitorControl 当前源码为唯一基准逐字节对照，不混用两家的参数
项目许可证文件缺失README 声明 MIT 但仓库根目录没有 LICENSE 文件，README 内链接失效补一份 LICENSE 文件（与本次改动无关，顺带修复）

12硬件安全性结论

写 VCP 0x10 亮度对显示器硬件为低风险操作：

  • 有记录的显示器固件异常案例全部来自输入源切换（VCP 0x60）或错误值域的其他控制码，检索范围内没有写亮度（含写 0、快速连写）导致硬件异常的报告 HIGH。
  • 存储磨损为理论顾虑（部分 EEPROM 写寿命约 10 万次量级），无实证失效案例；Lunar 作者对一台 LG 实测 5 年数百万次写入后存储正常。本方案一次会话仅两次写（降低 + 恢复），安全余量极大，不需要渐变动画。
  • 实现约束：只发 VCP 0x10，芯片地址硬编码 0x37（同总线 0x50 为 EDID 存储，写错地址有损坏 EDID 的历史案例）；写前必须读到 (current, max) 并 clamp，恢复直接写回 raw 值不做百分比换算（Gigabyte 值域案例：按错误尺度写入曾导致设置持久异常）。
  • 写 0 在绝大多数 LCD 上为背光最低仍可见；个别老款 Dell 固件把低值钳制到 30，属可接受降级。少数显示器收到 DDC 亮度命令会显示自己的 OSD 提示，主机端无规避手段，写入 FAQ 说明即可。

调研方法：6 个并行方向（Apple Silicon DDC、Intel DDC、系统原生亮度、软件调暗、开源许可证、代码库改动面）+ 完整性审查 + 2 个补充专题（硬件安全性、工具共存），共 9 个调研代理、294 次工具调用。证据分级：HIGH = 本机实测或亲读源码 / 官方文档；MEDIUM = 多个独立来源一致；关键 API 结论均在 M4 Pro + macOS 26.6 实测。主要来源：MonitorControl、m1ddc、AppleSiliconDDC、Lunar 源码，VESA MCCS 2.2a 规范，ddcutil 文档，Apple 开发者论坛。
